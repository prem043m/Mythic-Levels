# Mythic Levels — algorithms: where each is used, and why

**Destination vs route.** The 27 Gates (Beast → Human → Sage) stay as the fixed curriculum: they give the product its identity and its goal.
What adapts is the *route*: which practice is recommended, how long, and what is asked next. Adaptation only ever *suggests*; the progression engine is deterministic and authoritative, and no AI may grant XP, declare mastery or unlock a Gate.

| # | Algorithm | Where | Why this one | Known limits |
|---|-----------|-------|--------------|--------------|
| 1 | **Gate Mastery Protocol** (mandatory checks + weighted score) | `services/progression/mastery.js`, constants in `config/gmp.js` | A single percentage hides *why* a Gate is not done. Mandatory checks (all stages, practice days, accepted reflections, real-world action, ritual) give an explainable verdict; the weighted score (practice 20, consistency 15, reflection 15, application 20, final ritual 30) is a separate quality gate against `settings.masteryThreshold`. Pure + idempotent: it *decides*, the engine *applies once* (`completedAt` guard). | Weights are proposals; tune in `config/gmp.js`. |
| 2 | **Reflection rubric** (5 criteria, per-stage key criteria) | `services/progression/reflection.js` | A character count is trivially gamed (`aaaaaaaaaaaa`). The rubric checks *structure*: a specific moment, a named trigger/pattern, an action taken, a lesson, and on-theme. Accepted = on-theme AND ≥2 of the stage's 3 key criteria, so stages ask for different things. Copy-paste of an earlier reflection is detected (Jaccard ≥ 0.8). Feedback tells the player what to add. | It cannot verify truth, and word-overlap relevance is advisory: it rejects only text with *no* link to the Gate's vocabulary. Subtle off-topic text can pass; that is why reflections are only one of five signals and never grant XP alone. Optional AI feedback can be added later, never as authority. |
| 3 | **Specific-vocabulary filter** | `reflection.js › gateVocabulary` | A word found in >⅓ of all Gates ("because", "next") proves nothing about this Gate. Derived from the curriculum itself (document frequency), not a hand-made stoplist. | Lexical, not semantic. |
| 4 | **Ritual state machine** `preparing → active ⇄ paused → completed` (+ `abandoned`) | `services/progression/ritual.js`, wrapper `ritualAction` in `engine.js`, UI `pages/Ritual.jsx` | The final trial must be more than a checkbox and must survive real life. Active time = sum of recorded segments (survives reload, excludes pauses), required minutes come from each Gate's own trial duration (80%), a clock that moves backwards cannot cheat, `too-short`/`reflection-needs-revision` leave the attempt intact (recoverable), abandoned attempts never fail the Gate. Ritual score = mean of 5 visible parts (time, self-reported objective, observation, reflection, self-assessment). XP is paid once through the normal boss path; a later, better attempt only improves the score. | A browser cannot prove an offline act: the ritual is attested, recorded and reflected on, and the UI says so. |
| 5 | **Stage rules**: order enforced in the engine; ≤2 new stages per calendar day; locked Gates rejected before any record is created | `engine.js › completeQuest` | Before, order was UI-only, one sitting could finish a Gate (score ≈0.83 ≥ 0.70) and `ensureGate` auto-unlocked any Gate id. The cap of 2 (one regular + one catch-up) fixes minimum practice days at ⌈7/2⌉=4 with no extra magic number and avoids dead ends. | |
| 6 | **Streak over practice days** | `services/progression/streak.js` | Counts only *practice* days: skipping a rest day never breaks it; skipping a practice day starts a new run (progress is kept: kind `returned`). Local calendar keys avoid DST/timezone double-counting; same-day and backwards dates are no-ops. | Uses the device clock. |
| 7 | **Adaptive recommendation** (ordered rules, first match wins) | `services/progression/recommend.js`, shown on the Dashboard | Order = what unblocks the player most kindly: gentle re-entry after ≥3 days away → revise weak evidence → final ritual when ready → daily limit reached → next stage tuned by the weakest recent criterion. Every result carries a reason built from the player's own data. Difficulty is only *suggested* (3 strong accepted reflections), never auto-changed. | Rule-based on purpose (explainable, testable); a learned model could later propose candidates that these rules validate. |
| 8 | **Optimistic concurrency for sync** (revision + compare-and-swap) | `server/index.js › PUT /api/save`, `store/useGameStore.js` | A stale device could silently overwrite newer progress. Now a write succeeds only if the client saw the latest revision; otherwise `409 conflict` and the player explicitly chooses *keep this device* or *use the server*. | No automatic merge (merging two diverging histories safely needs per-event logs). |
| 9 | **Coach retrieval** (BM25-style ranking over Gate passages) | `server/coach/retriever.js` + provider seam | Retrieval-first answers with sources; no invented Gate knowledge; the Coach never touches progression state. A future LLM plugs into `getProvider()` with the same input. | Keyword-based. |
| 10 | **Email tokens** (single-use, hashed, expiring) + scrypt passwords | `server/auth.js` | Standard, safe verification/reset flow; reset signs out every device; no account enumeration. | |

## Tunable numbers awaiting product approval (`config/gmp.js`)
Weights 20/15/15/20/30 · ≤2 stages/day · ≥4 accepted reflections of 7 · ≥2 of 3 real-world stages · ritual minimum = 80% of the Gate's own trial duration (45 min → 36) · mastery threshold stays at the existing 70%.
The product brief proposed 60 minutes for the Gremlin ritual; the canonical Gate data says 45, so 45 is used.

## Not built yet
Per-Gate custom rituals beyond the shared framework (each already uses its own trial text and duration) · developmental memory across Gates · Arcana-completion ceremonies and unique art per Gate · analytics from events · server-side email reminders · automatic sync merge.
